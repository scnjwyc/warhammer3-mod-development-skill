# 外观缩放与战斗判定分别检查

模型看起来更大，不足以证明碰撞、质量、受击或动作也按比例变化。反过来，实体参数改变也不证明玩家能看到的所有外观已同步。先明确需求是外观缩放，还是同时改变战斗体积与物理表现。

## 两条活动链

| 链 | 调查内容 |
|---|---|
| 外观 | `unit_variants` / 角色 art set → `variants` 的缩放与文件 → variantmeshdefinition → wsmodel → RMV2、材质和贴图 |
| 战斗实体 | `land_units.man_entity`，坐骑经 `land_units.mount` → `mounts.entity`；再查 battle personality 与相关引擎/车辆记录 → `battle_entities` |

角色步行、坐骑、备用服装、战役和战斗可能走不同资源；从实际被选中的 variant/art set 出发，不只改同名模型。

实体字段逐项判断：`radius`、`height`、`shape/radii_ratio`、`mass`、`size`、`combat_reaction_radius`、投射物相交参数及移动/转向字段分别承担不同职责。不要把 `mass` 当半径，也不要无证据声称所有碰撞值自动随 `variants.scale` 变化。外观倍率不要求所有字段机械同比例乘算，尤其质量、速度、动画体型和击退阈值；选同类原版实体作基准并保留设计差异。

## 共享实体与人数

改实体前反查所有使用者，至少调查 land unit、mount、battle personality、battlefield engine 和 articulated vehicle 的实体引用。只想改一个 MOD 单位时，复制完整实体为自有 key，再只重定向目标引用；不能为了单个角色改共享原版实体而影响其他单位。若设计就是全体修改，记录范围并审查所有受影响对象。

人数、坐骑/器械数量、编队间距、每个实体生命与单位总生命另行检查 `main_units`、`land_units`、编队及实体记录。不要用放大外观替代人数/编队修改，也不要用固定公式推断最终总生命而跳过实际配置。

## LOD、贴图与动作

检查 wsmodel 的全部 LOD 与各材质贴图路径，而不只 LOD0；遗漏低 LOD 会在远距离回退到旧模型/材质。检查 variants 的低模路径、备用外观和坐骑文件。仅修改自有目标资源，保留确有需要的共享引用；无意覆盖原版同路径资源时改为自有路径并更新完整引用链。

缩放后如出现手指扭曲或骨架拉伸，先排除错误动作键/挂点，再用目标环境的模型工具检查活动骨架、权重与骨索引。移动射击姿态问题先查 [动作槽与容器](animation-and-mounts.md#移动射击的分层排查)，不直接归因于顶点权重。贴图另核对真实压缩格式、Alpha、尺寸与 Mip，避免把材质问题混入实体参数判断。

## 验收分开记录

离线分别报告活动资源、scale、实体字段、共享引用范围、LOD/贴图完整性和 Pack 读回。用户实机分别检查外观大小、接触/转向/冲锋、受击/击退、远近 LOD 以及步行/坐骑动作。未经实机结果，不把 DB 字段合理或模型预览正常写成战斗判定已经正确。
